# The spike — read at `plan` step 2

The spike tries to break each claim of the brief — *this sketch does X*, *these tests break and no others* — before it is frozen: five questions, each answered by an artefact pasted into a named slot, not a sentence you write.

## Mechanics

- **Patch, never edit.** Put the sketch into a run from the scratch directory, through an explicit opt-in (the house rules name the mechanism) — never through a file the tooling discovers by itself. Run the unpatched control first; then prove every variant (patch, copy, mutant) was live: one check that passes with it and fails without; a batch reading all equal to the control's is a liveness failure until shown otherwise. Afterwards the tree is unchanged.
- **A stand-in is marked and seeded.** When the dataset a rule names cannot be reached now, dry-run on a stand-in and mark the rule `DRY-RUN ON STAND-IN — real run pending, orchestrator only`. Seed it with every kind in your partition table (question 2) before trusting a PASS.
- **Bound every probe that can amplify.** Whenever the diff adds or changes a repeat over input — a regex quantifier, a loop over user-sized data, a recursion, a call handing user-sized input to a library: every cost probe runs in a subprocess under wall-clock and memory caps at geometric sizes, with one input the code accepts, one it rejects only after doing the most work it can (a long valid prefix, the deepest nesting, the widest fan-out), and one at each limit the called code declares, each input dimension grown alone and two at once. It reads CPU time — the clock named with its documented scope, process or thread — and peak memory, head against base on the same input; a ratio to any other control is not a cost reading. The brief states the bound, and FAIL is the smallest size past it. A DEFAULT that accepts a cost cites both readings. A committed cost test asserts a count of work where the code exposes one, else a ratio of sizes (4n against n, best of k, its margin beside it); its absolute timeout is a hang guard, never the claim.
- **Write what cannot be seen.** Non-printing characters and non-ASCII whitespace are `U+XXXX` in prose and escapes in code, enforced by the house rules' file check.

## Five ways a brief lies

1. **Unrun.** *Did this exact thing execute, in full?* A sketch, a rule, a metric definition, an inherited test — each counts as executed only if its literal body ran, every assertion included. **Artefact:** the command and its output, per claim — the sketch's `EXECUTED (inputs: …)` marker in §2.
2. **Blind partition.** *Which kinds of input never met this claim?* List the distinct ways data reaches the line you are changing and the distinct shapes a result can take when it leaves — including the boring ones: an empty field, another source, an unexpected place (a nested, quoted or escaped context; another field). Derive the list from the path the data travels and the boundaries it crosses, and cross it with your hostile inputs. A container kind needs a one-item and a many-item row; a path argument, a row per way it fails: missing, a directory, unreadable, undecodable. A predicate that classifies its input (accepted / refused, healthy / unhealthy) is run over the healthy population on the base — every fixture, every stand-in, the sweep — and its false positives are counted before it is frozen. A sweep is generated from an enumeration named in the table with its source path, member count and members hit, taken where input forms differ — a parser's rules, not its output types; a format's structural tokens and whitespace; a schema's enum values; every writer of the field — never hand-picked; so is every value the changed code writes into or matches against its input's channel (sentinels, placeholders, delimiters, escapes), whole, truncated and joined to a real one. A rule that decides one unit of a sequence (a line, a block, a token, a call) is enumerated over every sequence of unit kinds to length 3 at least, each unit's enclosing context varied on its own, before a sampled fuzz over the same alphabet is trusted. **Artefact:** the §2 Partition table: kind · how it reaches the line · executed case · reading; a row that could not be run, or that a sweep never hit, reads `NOT RUN (why)`.
3. **Weak oracle.** *Is the check as strong as the sentence?* Quote the comparison you ran, not a paraphrase of it. A claim holding a class word — any, every, all, always, never, none, nothing, beyond — names the §7 line or `enumerate:` row that searched for its counterexample. The oracle of a sweep is a per-field diff against the base — every value the sketch drops, changes or adds — never a pattern for what damage looks like; a differing record is classified by the oracle its attack line names, never by the expected reading. Every rule — every conjunct, metric and sub-check it reads — has one reading where it says FAIL (an equality of counts needs a non-zero precondition: 0 == 0 evaluates nothing): the nearest plausible wrong fix, or the unfixed base on the same data — never an absurd mutant, never a stub. An oracle that executes a component the change depends on cannot grade what that component decides: name an independent one (another implementation, the spec's examples as written, a relation between two runs) or read `NOT RUN (no independent oracle)`. **Artefact:** the PASS reading and the FAIL reading, side by side, in the rule's §5 row.
4. **Blind dataset.** *Could this data show the failure at all?* If the nearest wrong fix also reads PASS here, the rule has no power on this dataset: say which slice binds, or delete the rule and list the test that binds in its place — a stand-in is yours to build, but adding a dataset to a gate is a ruling. The dataset is reachable from a fresh worktree of the base: committed, or generated by a committed command and seed. **Artefact:** the wrong fix's reading on the same data.
5. **Unfollowed state.** *What happens next?* When a probe leaves something behind — a stored value, a file, a log line — follow it through the next read, the next write and the next start before you name its impact in plan step 3's (d) words. When the change writes, state what a repeated write should do and run every input through it twice: a rewrite's second pass changes nothing (f(f(x)) == f(x)); an append is refused, collapsed by its key, or recorded twice by design; when it adds a status or a derived field, read that field after the next write through the public API, not only after the next start. **Artefact:** the three follow-ups, the second-pass reading and the post-write reading — or, if nothing is left behind, the check that shows it.

A finding that fits none of the five goes in the lessons file; that is how this list grows.
