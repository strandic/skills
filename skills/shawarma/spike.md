# The spike — read at `plan` step 2

A brief is a set of claims — *this sketch does X*, *these tests break and no others* — that lanes copy verbatim. The spike tries to break each before it is frozen: five questions, each answered by an artefact pasted into a named slot of the brief, not a sentence you write.

## Mechanics

- **Patch, never edit.** Put the sketch into a run from the scratch directory, through an explicit opt-in (the house rules name the mechanism) — never through a file the tooling discovers by itself. Run the unpatched control first; then prove the patch was live (one check that passes with it and fails without). Afterwards the tree is unchanged.
- **A stand-in is marked and seeded.** When the dataset a rule names cannot be reached now, dry-run on a stand-in and mark the rule `DRY-RUN ON STAND-IN — real run pending, orchestrator only`. Seed it with every kind in your partition table (question 2) before trusting a PASS. A stand-in never counts as the live-data run.
- **Bound every probe that can amplify.** Whenever the diff adds or changes a repeat over input — a regex quantifier, a loop over user-sized data, a recursion, a call handing user-sized input to a library — whatever the ticket is about: every cost probe runs in a subprocess under wall-clock and memory caps at geometric sizes, with one input the code accepts, one it rejects only after doing the most work it can (a long valid prefix, the deepest nesting, the widest fan-out), and one at each limit the called code declares, each input dimension grown alone and two at once. It reads time and peak memory against the base; the brief states the bound, and FAIL is the smallest size past it. A DEFAULT that accepts a cost cites both readings. A committed timing test runs under the wall-clock bound the house rules name.
- **Write what cannot be seen.** Non-printing characters and non-ASCII whitespace are `U+XXXX` in prose and escapes in code; a file check the house rules name fails any file holding one literally, and any test missing one its brief names.

## Five ways a brief lies

1. **Unrun.** *Did this exact thing execute, in full?* A sketch, a rule, a metric definition, an inherited test — each counts as executed only if its literal body ran, every assertion included. **Artefact:** the command and its output, per claim — the sketch's `EXECUTED (inputs: …)` marker in §2.
2. **Blind partition.** *Which kinds of input never met this claim?* List the distinct ways data reaches the line you are changing and the distinct shapes a result can take when it leaves — including the boring ones: the field empty, the value arriving from a different source, the value turning up where you are not looking (a nested, quoted or escaped context; another field). Derive the list from the path the data travels and the boundaries it crosses — every writer of a field, not only the client — and cross it with your hostile inputs. A container kind needs a one-item and a many-item row; a path argument, a row per way it fails: missing, a directory, unreadable, undecodable. A predicate that classifies its input (accepted / refused, healthy / unhealthy) is run over the healthy population on the base — every fixture, every stand-in, the sweep — and its false positives are counted before it is frozen. A sweep is generated from an enumeration named in the table (a parser's token or node types, a schema's enum values, every writer of the field), never hand-picked; for a rule over a structured format, the alphabet is the format's own grammar — every structural token (delimiters, nesting and quoting markers, escapes) as well as whitespace — with the spec section cited. A rule that decides one unit of a sequence (a line, a block, a token, a call) is enumerated over every sequence of unit kinds to length 3 at least, each unit's enclosing context varied on its own, before a sampled fuzz over the same alphabet is trusted. **Artefact:** the §2 Partition table: kind · how it reaches the line · executed case · reading; a sketch is `EXECUTED` only over its rows; a row that could not be run reads `NOT RUN (why)`.
3. **Weak oracle.** *Is the check as strong as the sentence?* Quote the comparison you ran, not a paraphrase of it — a §4 assertion is the executed text. A claim holding a class word — any, every, all, always, never, none, nothing, beyond — names the §7 line or `enumerate:` row that searched for its counterexample. The oracle of a sweep is a per-field diff against the base — every value the sketch drops, changes or adds — never a pattern for what damage looks like; a differing record is classified by the oracle its attack line names, never by the expected reading. Every rule — every conjunct, metric and sub-check it reads — has one reading where it says FAIL (an equality of counts needs a non-zero precondition: 0 == 0 evaluates nothing): the nearest plausible wrong fix, or the unfixed base on the same data — never an absurd mutant, never a stub. **Artefact:** the PASS reading and the FAIL reading, side by side, in the rule's §5 row.
4. **Blind dataset.** *Could this data show the failure at all?* If the nearest wrong fix also reads PASS here, the rule has no power on this dataset: say which slice binds, or delete the rule and list the test that binds in its place — a stand-in is yours to build, but adding a dataset to a gate is a ruling. **Artefact:** the wrong fix's reading on the same data.
5. **Unfollowed state.** *What happens next?* When a probe leaves something behind — a stored value, a file, a log line — follow it through the next read, the next write and the next start before you name its impact in plan step 3's (d) words. When the change writes, state what a repeated write should do and run every input through it twice: a rewrite's second pass changes nothing (f(f(x)) == f(x)); an append is refused, collapsed by its key, or recorded twice by design; when it adds a status or a derived field, read that field after the next write through the public API, not only after the next start. **Artefact:** the three follow-ups, the second-pass reading and the post-write reading — or, if nothing is left behind, the check that shows it.

A finding that fits none of the five goes in the lessons file; that is how this list grows.
