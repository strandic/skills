One ticket → one **brief** → one **run** → one PR. The brief is the whole contract: an agent that has read only it and the files it names can do its part. Three branches: `plan <ticket>` ends in a brief, a trivial call or questions; `run <ticket>` ends at PR open; `retro` reviews the method. **Invoking `run` is the go.** The human's checkpoints are the grill, rulings and `run` — never the PR: a decision "left for the PR" is one you made alone.

## House rules

Before any branch, read the repo's `docs/plans/README.md` if it exists: tracker cadence and note texts, worktree bootstrap, test and lint commands, how to patch a sketch into a run, the scratch directory, the hostile corpus, data rules, cleanup. This skill says *what*; that file says *how* in this repo — cite its commands, never restate them. Defaults when there is none, on the base branch: brief `docs/plans/<date>-<ticket>-<name>/plan.md`, lessons `docs/plans/lessons.md`, retros `docs/retros/<date>-<topic>/`.

## Asking the human

One format, in prose, free-text answers welcome: the reading · the mechanism · which side is wrong — the rule, the ticket or the code · the options, one-line consequence and executed reading (or `unexecuted`) each, recommendation first · where the residue goes. Each item is marked **RULING** — it changes a numbered ruling, a frozen line or a gate, and waits for an answer — or **DEFAULT** — the recommendation stands unless struck; `go` or silence accepts it, and a struck DEFAULT becomes a RULING. A DEFAULT may add a test, never flip one. For a pre-registered threshold, recommend a reading; never draft the replacement number before the ruling.

## Triage

- **Trivial** — judged by reading, never by spiking: the ticket names the change, it fits one small diff with one test that will be red on the base (say how it fails; nothing is run at triage), and its worst case, following the changed error paths by reading, is an inconvenience. Anything beyond the ticket's words is a one-line question in the note, never folded in. The note gives the sites · the red test · the worst case · `unruled:` (below). Note on the ticket per house rules; stop. On the go, do it per house rules; the readings standing in for the review wave are claimed on the ticket as in run step 6.
- **Settled?** (i) The design is decided — measured evidence with weighed options, an ADR, or the human's rulings — AND (ii) the gate is evaluable today: it names its metric and dataset unambiguously and the data exists (no dataset? a unit test plus one executed stand-in probe). An ADR waives (i)'s evidence, never (ii); a gate observed to read two ways on executed data is not settled. Not settled ⇒ `grill-me` as wave −1, evidence and cheap hostile probes gathered first; outcome onto the ticket; then plan. The brief never settles a design.
- **Error directions.** The grill writes a design's two error directions and which one corrupts output; the frozen rule never errs that way.
- **Siblings** fold into one brief and one PR only when they share a file or are not shippable apart, and never when the sibling's fix errs the corrupting way.

## plan <ticket>

1. Read the ticket, the files it names, the house rules, and the lessons file's entries since its last retro marker — a lesson whose class matches the change is a spike input, cited in §2. Triage. Refreshing an old brief: nothing is inherited.
2. **Spike before you freeze.** Read [spike.md](spike.md) now. Orchestrator only; never edit tracked files. Execute every sketch. Run the suite with the sketch patched in — sources AND every new fixture, in its real location: what breaks goes in "Existing tests that change", and every flipped expectation there is a ruling. Then run the changed tests with the sketch out and the table's edits in: that pasted failing list, with the §4 reds, is the predicted red set. Dry-run every gate rule with the fix patched in and show one reading where it FAILS. Put each claim the brief will make through spike.md's five questions and the repo's hostile corpus. Then write §7's **attack lines** — each one input or one verb sequence and the oracle that grades it (`→ oracle <name>`); your expected reading stays in your notes, never in the line; a class word ("any", "every", "beyond") is an `enumerate:` row naming its source — and launch the **attack lane** (Sonnet; patches from scratch per the house rules, tree unchanged): it executes every line and returns raw values against the named oracle, or `NOT RUN (why)` naming the missing resource; you grade. Readings go in §2 beside the sketch; a reading that changes a sketch sends the changed lines back through the five questions and the lane; a line whose reading holds becomes a §4 test (red or guard), so nobody re-runs it.
3. **A finding stops the plan** only when it (a) contradicts or falls outside a ruling or the ticket's stated design; (b) makes a gate rule ambiguous, unevaluable, or FAIL with the intended fix in; (c) shows wrong output — output that tells its reader something false, however harmless — or a forbidden state reachable through the change, including a value this API would refuse as input but writes itself; you never accept either, and a ruling that accepts one shape does not cover a new one: change the sketch until the probe passes, or ask; (d) shows an impact the ticket did not weigh: data loss, cannot start, unavailable to others, a leak, silently wrong results. Everything else is recorded in the brief as what you saw. A pre-existing bug is proposed as a new ticket; folding it in is a ruling.
4. **Ending: questions.** Finish the spike first, then ask; the re-spike on the ruled design may ask again. More than three questions in one round means not settled: grill. Note on the ticket "Plan paused: <n> questions" with the readings; commit, push, stop. The answers go onto the ticket's settled section verbatim — an explicit answer, "go with reco" included, is a ruling; only silence on a DEFAULT is a default; re-run the spike on the ruled design; continue.
5. **Ending: brief.** Write it from [brief-template.md](brief-template.md), every section. Every gate rule is **written before the first run**: a counted threshold is `FLOOR = measured − 2 cases`, an invariant has no floor; the live-data run is orchestrator-only, aggregates and structure only. A brief is frozen only when every §7 attack line has its reading in §2 or a `NOT RUN (why)`, every Partition row carries its line's reading, and §7's lane cells are template text with ids filled — a class word there is an unmarked attack line; §2 holds its Partition table; every §4 red assertion is the executed assertion text, never a whole test file; every §5 rule carries its command, its settle clause and a FAIL reading on its named data — a rule with none is deleted and the binding test listed. Every plan ending — brief, trivial, questions — ends with `unruled: <one item> — default <x>` or `unruled: none`. Note on the ticket and commit per house rules; stop.

### Wave rules (hard)

- **Single writer by default.** One test lane, then ONE implementer — a subagent, never the orchestrator who wrote the brief. Several implementers only when the brief argues independence: disjoint files AND no shared new symbol, key or contract.
- **Tests first, blind.** The test lane writes against the brief only, never sees an implementation, and owns the edits to existing tests. The orchestrator commits its work, runs the house rules' escape check on it, and observes the red set on that commit, diffed by name against the predicted one: every *red* fails for the stated reason (a collection or import error is a finding — import new symbols inside the test), every *guard* is green. No lane turns a guard red silently.
- **Workers** edit their files and run the commands their prompt names. No real data, no live server. Blocked by anything outside their files (a test bug, a contract that cannot be honoured), they stop and report, never fix. The attack lane is a worker with no files: it patches from scratch and leaves the tree unchanged.
- **A review wave, always.** Reviewers never edit the repo, not even temporarily: they patch from a scratch directory, and every finding carries a minimal runnable reproduction. *Adversarial*, when the brief's worst-impact line calls for it: attacks **executed, not reasoned** — the `NOT RUN` lines, the enumerations, the hostile corpus; an all-clear with no observed run does not count. *Code review*, only when the adversarial lane does not run: the template's 3b row. Each review lane writes its scripts and output under the plan folder's `reports/<lane>/`, aggregates only; the orchestrator commits them and checks the tree is otherwise unchanged.
- **Orchestrator-only** — git, ticket writes, the spike, the live-data run, the PR.

## run <ticket>

Precondition: the brief is on the base branch and the ticket says awaiting go.

1. **Wave 0.** Branch and worktree per house rules, with everything the suite needs installed; ticket → in progress.
2. **Wave 1t, then 1i.** Lane prompt: *"Work only in `<worktree>`. Read `<brief path>`. You are lane <id>. Touch only your files. Run `<test command>`, `<lint command>` and `<escape check>` on the files you wrote — done means all three pass. Base readings: `git show <base>:<path>`; never `stash`, `checkout`, `add`, `commit`, `reset`, or anything that changes the tree or index. Report the exact tests failing before and after, and anything outside your files that blocked you — stop, do not fix it."* A blocked implementer's test bug → relaunch the test lane with the evidence.
3. **Wave 2, integrate.** Full suite and lint, reported as passed AND skipped against the base, same toolchain, each run's results written to the reports folder so every failure has a name: a new skip or a new failure is a finding. Commit per house rules, one commit per lane deliverable.
4. **Wave 3, review.** Label every finding APPLY, DECLINE, TICKET or RULING — the four labels only; a DECLINE adds one class word: `unreachable` · `pre-existing` · `out-of-scope` · `style` · `superseded` · `false-positive`; an executed all-clear is verification, not a row. An applied behaviour change ships a regression test built from the reviewer's reproduction, shown red on the pre-fix source.
5. **Stop for a RULING** whenever a change would mean editing a numbered ruling on the ticket, a line of §3, a line a §3 row points at by reference, a line of §8, or a gate rule or command — a rule that read FAIL, could not be run, or passed but is wrong — and for any finding in a plan-step-3 (c)/(d) class. A §2 amendment outside all of those is a DEFAULT: it ships its red-first regression test, gets a §9 row marked `default`, and is listed in the next stop message where the human may strike it. Record each ruling in §9 and put amended text in later lane prompts; the sections above it are not edited after `run` — hygiene aside, never §3 or §4 text; and observations never go in the brief.
6. **Wave 4, gate and PR.** The live-data run on the final commit — each §5 rule by its own command line, on the tools committed there, read per its settle clause; a scratch copy, an altered flag or a second reading after a non-PASS is a RULING stop, recorded in §9 even when granted; a later code commit voids the run. PR body: tickets, brief path · **What** · **Verification** — suite and lint against the base, each §5 rule with its command line and counts, each lane reading by its path under `reports/`; a reading without a command or a path is not claimed · a table (finding or deviation · label · what was done), written only here · **Follow-up**. The stop message and the ticket link to that table and list any commits made after the review round, marked unreviewed, and every DEFAULT row. Ticket per house rules. Stop.

The human merges. Cleanup is a house rule, and ends by appending one line of run stats and any lessons to the lessons file.

## retro

On `retro`, run [retro-workflow.js](retro-workflow.js); the human rules; the record goes in the retros folder. A pre-registered measure names the class that counts, an impact floor, and its reading on the runs in hand before it is frozen; its consequence is honoured as written. This skill changes only at a retro, in words a stranger's repo could use: a new rule names the class of failure it prevents, never the case that prompted it. The retro reports word counts per file before and after and cuts at least as many words as it adds, unless the human rules otherwise.
